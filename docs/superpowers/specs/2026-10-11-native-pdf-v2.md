# Native PDF evidence v2: finite source-declared text contract

Prospective implementation design, recorded before implementation. Closed v1 captures are immutable and are not reinterpreted. This change authorizes no native/provider calls, orders, deployment, OCR, vision, new dependency or increased resource limit.

`native_text_complete` means that every invoked native text-show byte is decoded through a validated source-declared character mapping, in content invocation order, with exact source-byte and Unicode provenance. It does not certify that glyph outlines visually resemble the declared Unicode. The latter limitation applies equally to ToUnicode mappings. Font names never establish identity. `visual_meaning_verified` remains false. Embedded font hint programs are inventoried and hashed, never executed; glyph bounds are explicitly declared unhinted bounds, not rasterized bounds.

The finite font subset is standard fourteen Latin Type1 fonts with their standard/WinAnsi declarations, nonsymbolic embedded TrueType with WinAnsi and a consistent Unicode format-4 cmap, and Identity-H Type0/CIDFontType2 with an explicit finite ToUnicode mapping and validated CID-to-glyph mapping. All used codes require mappings, valid widths and structurally valid glyphs. Ambiguous, missing, contradictory or malformed maps, unsupported formats and dependencies fail technically. SFNT ranges/checksums, relevant head/maxp/hhea/hmtx/loca/cmap and glyph structures, composite references and cycles are checked. Font and CMap decoded bytes count against the existing aggregate stream bound. No glyph-shape recognition is claimed.

Every Tj, TJ, quote and double-quote show is reconciled directly with a deterministic Unicode transcript and inventory of source bytes, font identity, operator/invocation, matrices, spacing, offsets and TJ adjustments. Inferred separators are distinguished from source text; no pypdf nonempty-text proxy establishes completeness. All invoked streams, image/form dependencies and dictionaries remain bounded and fail closed. Only exact supported transparency groups, normal blend mode and explicitly typed inert marked properties are admitted.

The advanced font/operator path retains visual-layout obligations, with complete geometry/state provenance. Existing narrow plain standard-font layout acceptance remains independently checked. Positioned layout, vector painting, clips, overpainting, opacity and other valid unresolved visual features cannot waive an extraction/font/parser gap. Advanced embedded fonts do not become supported plain layouts merely from declared bounds. All parser, truncation, deadline, stream-budget and unsupported-capability failures retain precedence over visual findings.

Implementation sequence: (1) matched synthetic font/text counterexamples fail before implementation; (2) finite font/CMap validator and exact show/state integration; (3) focused and existing PDF suites; (4) exact two retained samples in fixed offline 28-second shared/35-second outer/30-second CPU bounds, producing a new private diagnostic with no acceptance claim; (5) independent adversarial review and prospective proof recomputation. The scanned sample's declared decoded image size remains above the unchanged cap and its unvalidated codec remains a failure.

The initial strict prototype rejected the first retained font's stale SFNT binary-search hints (14 tables, declared 256/4/128 versus computed 128/3/96). Before further acceptance, the coordinator adjudicated this against [Microsoft's OpenType table-directory specification](https://learn.microsoft.com/en-us/typography/opentype/spec/otff): parsers are explicitly advised to derive these optimization hints from `numTables`, not rely on the serialized values. V2 therefore records declared and derived hints and uses only the validated directory count/ranges. Hint mismatches do not authorize table, checksum, mapping or glyph repair. Malformed substantive font structures still fail.

## Implemented proof and review boundaries

The finite source declarations follow PDF 1.7 / ISO 32000-1 sections 9.6.6.4 and 9.10 ([Adobe's published standard](https://developer.adobe.com/document-services/docs/assets/35e4369068f86065372c18787171a17e/PDF_ISO_32000-1.pdf)). Standard fourteen font advances use the existing pinned pypdf Adobe core-font metrics, separately from conservative one-em plain-layout bounds. Every show and geometry operator records its exact decoded content-stream byte range. Stranded operands at end of stream fail instead of being silently dropped by a general parser. Per-glyph inventory expansion is checked against the existing provenance bound before allocation.

Adversarial review closed reproduced gaps in external/opaque font, CMap and page/form streams; non-finite derived transforms; harmless operator prefixes incorrectly classified as positioned text; CMYK white incorrectly treated as black; and unused rendering-mode changes incorrectly treated as visible content. Finite dictionaries and lossless filters are checked before decoding. Geometry state is validated for every transform, even without text. Visual findings arise from actual shows and geometry rather than an operator-set mismatch. Nondefault text visibility that has not been proved remains a technical support limitation. No general image-visibility engine or rasterized-font interpreter is added.

The fixed retained-source diagnostic at `data/forward-readiness/supported-native-pdf-v2-fitness-reviewed/report.json` is prospective parser fitness only. Within unchanged 28-second shared / 35-second outer / 30-second CPU bounds, the first retained PDF produced all seven pages, 878 shows and 7,600 characters, with 409,229 aggregate decoded stream bytes and no residual technical limitation. It retains clipping, marked-content, positioned-layout and vector findings, with supported text layout false and visual meaning unverified. The second retained PDF remains `pdf_unsupported_image_codec`; its previously documented aggregate decoded-pixel bound is unchanged. Neither diagnostic is a native acceptance run, a supported analysis, a durable disposition acceptance or a reinterpretation of a closed capture. Independent review accepted the exact application-file hashes recorded in that final diagnostic for this finite contract; root owns full-suite verification and further acceptance gates.
